# Aphelion Mealprep

A meal-plan optimizer. Aphelion Mealprep finds the most cost-effective meal
plan for your nutritional needs using FDC macronutrient data and a price table.

## What it does

Aphelion Mealprep accepts a natural-language request for a meal plan with
calorie, protein, carb, fat, and price goals. It returns a meal plan that
satisfies all requested nutritional goals for the lowest possible price. If
no such plan exists, it says so directly. You can also exclude specific 
ingredients and limit any single ingredient's share of total calories to 
increase variety.

## Architecture

Once the user enters their request, it's processed by an LLM to build a
`MealPlanRequest` object containing their macronutrient and price goals.
OR-Tools GLOP then solves for the minimum-price combination of ingredients
that satisfies all requested targets.

Using OR-Tools to optimize rather than the LLM removes the risk of
hallucinated or fabricated numbers, and it ensures infeasible requests are
caught and reported. Successful solves return `SolverSuccess`, which is
formatted into a plain-text string for the user to read.
Failed solves tell the user directly that their plan wasn't feasible.

## Setup

### Prerequisites
- Python 3.11+
- An Anthropic API key

### Installation

```bash
git clone https://github.com/AlvinL5/Aphelion-Mealprep.git
cd Aphelion-Mealprep
python -m venv venv
source venv/bin/activate  # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

### Environment variables

Create a `.env` file in the project root:

```
ANTHROPIC_API_KEY=your_key_here
```

### Running the server

```bash
uvicorn main:app --reload
```

The API is available at `http://localhost:8000`, with interactive docs
(auto-generated by FastAPI) at `http://localhost:8000/docs`.

## API Usage

### `POST /plan`

Takes a single free-text request and returns a plain-text meal plan, or an
explanation of why one wasn't possible.

#### Request body

```json
{
  "user_input": "I want 2500-3000 calories a day, at least 120g protein, at least 200g carbs, under 30g fat, and under $30. No whey protein, lentils, chickpeas, bacon, or black beans."
}
```

`user_input` is the only field. The LLM parser extracts only what's
explicitly stated — it's instructed not to infer or estimate values the user
didn't mention — and builds a `MealPlanRequest` internally:

| Field | Type | Notes |
|---|---|---|
| `min_calories`, `max_calories` | float | Required internally; a request with no calorie information will fail to parse |
| `min_protein`, `min_carbs`, `min_fat` | float | Default 0 if not mentioned |
| `max_protein`, `max_carbs`, `max_fat` | float or null | Only set if you state an upper bound |
| `max_price` | float or null | Budget ceiling |
| `calorie_percent_max` | float (0–1) or null | Caps any single ingredient at this fraction of total calories, for variety |
| `excluded_ingredients` | list[str] | Ingredients to exclude entirely |

#### Successful response — `200 OK`

```json
{
  "plan": "Your optimal mealplan is:\n193g of Egg, whole, raw\n734g of Pasta, dry, enriched\nCalorie Total: 3000\nProtein Total: 120g\nCarbs Total: 550g\nFat Total: 29g\nTotal Price: $2.55\n"
}
```

#### Error responses — `422 Unprocessable Entity`

Both failure modes return the same shape with different message texts.

```json
{ "detail": "Not possible with given constraints." }
```

Returned when the request is well-formed but no ingredient combination
satisfies it (e.g. the budget is too low for the calorie floor).

```json
{ "detail": "1 validation error for MealPlanRequest\nmax_protein\n  Value error, protein max cannot be less than protein min ..." }
```

Returned when the LLM couldn't produce a valid, internally-consistent
`MealPlanRequest` — either it failed to extract usable output at all, or the
extracted values conflict (e.g. a stated max below a stated min).

## Project Structure

```
├── main.py                       # FastAPI app, single POST /plan endpoint
├── solver.py                     # OR-Tools GLOP solver — returns SolverSuccess or SolverFailure
├── llm/
│   ├── parser.py                  # Anthropic API call — parses NL input into a ParseSchema, then a MealPlanRequest
│   ├── parse_schema.py            # ParseSchema — the LLM's structured tool-call output before conversion to MealPlanRequest
│   └── format_response.py         # Formats SolverSuccess into a plain-text string — no LLM call
├── models/
│   ├── meal_plan_request.py       # MealPlanRequest — validated nutrition/price constraints
│   ├── solver_success.py          # SolverSuccess — ingredient quantities and nutrient/price totals
│   ├── solver_failure.py          # SolverFailure — infeasibility message
│   ├── parsing_error.py           # ParsingError — NL parsing/validation failure message
│   └── nutrient.py                # NutrientRecord — used when building the ingredient dataset
├── data/
│   ├── ingredients.csv             # ~58 ingredients, USDA FoodData Central macros
│   ├── prices.csv                  # Manually-entered prices per 100g
│   └── fdc_mapping.py              # Ingredient → FDC ID mapping used to build ingredients.csv
├── scripts/
│   ├── fetch_nutrients.py          # Pulls macro data from USDA FDC and writes ingredients.csv
│   └── check_ids.py                # Validates FDC IDs used in fdc_mapping.py
└── tests/
    ├── test_solver.py              # Feasible, budget-infeasible, macro-infeasible cases
    ├── test_format_response.py     # String output formatting
    ├── test_parser.py              # NL → MealPlanRequest conversion, including min/max conflicts
    └── test_endpoints.py           # Full request/response cycle via TestClient, with parser/solver mocked
```

## Testing

```bash
pytest
```

Covered:

- **Solver** (`test_solver.py`) — a feasible request, a budget-infeasible request, and a macro-infeasible request (protein floor unreachable with the relevant ingredient excluded). Infeasibility tests currently only assert that a `SolverFailure` is returned, not which specific constraint caused it.
- **Response formatting** (`test_format_response.py`) — verifies the plain-text output string matches expected values and rounding.
- **NL parsing** (`test_parser.py`) — stated min/max ranges, approximate values (converted to a ±10% range), and a case where the LLM extracts a self-contradictory range (min > max), which is expected to return a `ParsingError`.
- **Endpoint** (`test_endpoints.py`) — the full `/plan` request/response cycle via `TestClient`, with the parser and solver mocked, covering the parse-error, solver-error, and success paths.

## Future Improvements

- **Smarter request interpretation** — e.g. inferring a caloric deficit from a stated weight-loss goal and body weight. 
- **More realistic real-world constraints** — package-size discretization (solver currently only considers continuous values)
- **More data** — the ingredient list and price table are currently small and sourced from a single store; expanding both would improve plan quality and realism.
